<p class="lede">One of the production systems I have built never talks to the internet. It is a retrieval-augmented assistant for an organisation whose documents are not allowed to leave the building, so every embedding and every answer comes from an open-weight model running on the same machine as the user. When people ask whether that is a toy, my answer is no — but only because of a decision most tutorials treat as a footnote: how the model is quantized, and whether it actually fits in memory with the context the job needs.</p>

The argument of this article is simple. For workloads bound by privacy, data residency, offline operation or predictable cost, a well-quantized open-weight model on ordinary Windows hardware is now a credible production option. Not for everything, and not because local is cheaper — it usually is not. It is credible because three things have matured at once: quantization formats that lose almost nothing at 4–5 bits, runtimes that install with one command and expose an OpenAI-compatible API, and open-weight models released under permissive licences, sometimes already quantized by the vendor. The corollary is the part people get wrong: success depends less on which model you pick than on the quantization and memory budget you fit it into.

Here is the route. I start with why local inference matters now and what the honest economics look like. I then lay out the evidence on quantization — size, quality and speed — including a result that overturns a popular rule of thumb. I offer a decision framework, then go deep on four dimensions: how quantization actually works, the memory arithmetic, hardware tiers on Windows, and runtimes and serving. I close with cases, counterpoints, implications by role, a 90-day plan and the limits of what this evidence can tell you.

## Context: why this matters now

There are four legitimate reasons to run a model locally, and only one of them is cost.

**Residency and privacy.** In regulated settings — health, legal, finance, government — sending document text to a third-party API is often a compliance question before it is an engineering one. A local model removes the question: no egress, no processor agreement, no cross-border transfer. **Offline and edge operation.** Field teams, ships, clinics with poor connectivity and air-gapped networks cannot depend on an API at all. **Latency and control.** A local model has no rate limits, no surprise deprecations and no queue you do not own. **Cost** at very high, steady volume — but this is the weakest of the four, and I want to be precise about why.

The supply side has shifted decisively. Vendors now ship models designed to be quantized. Google released quantization-aware-trained (QAT) versions of Gemma 3 in April 2025, cutting the weights of the 27B model from 54 GB to 14.1 GB so that it runs on a single 24 GB RTX 3090 ([Google](https://developers.googleblog.com/en/gemma-3-quantized-aware-trained-state-of-the-art-ai-to-consumer-gpus/)). OpenAI’s gpt-oss models were post-trained with MXFP4 quantization of their mixture-of-experts weights; the 20B model (21B parameters, 3.6B active) is stated to run within 16 GB of memory, under Apache-2.0 ([model card](https://huggingface.co/openai/gpt-oss-20b)). The 2026 open-weight field — Qwen, Gemma 4 with official QAT q4_0 GGUFs, Mistral Small 4, DeepSeek, gpt-oss — is large and mostly permissively licensed.

Now the economics, honestly. Small hosted models have become extraordinarily cheap. At October 2026 list prices, Claude Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/overview)); Gemini 3.5 Flash-Lite is $0.30 and $2.50 ([Google](https://ai.google.dev/gemini-api/docs/models)). Take a typical retrieval-augmented query — about 3,000 tokens of prompt and retrieved context, 300 tokens of answer — and a 16 GB RTX 5060 Ti, which launched at $429 ([PCGamesN](https://www.pcgamesn.com/nvidia/geforce-rtx-5060-ti-guide)). Read Exhibit 2 carefully, because it cuts both ways. Against frontier-priced models, a modest GPU pays back within tens of thousands of queries — a few months for a busy internal tool. Against the cheapest hosted tier, it takes close to a million. So the cost case for local is narrow: high, steady volume on tasks where a small model is good enough. The stronger case is almost always the first three reasons — residency, offline, control — where the hosted option is not on the table at all. If you are choosing local to save money on a low-volume workload with no data constraints, you are probably making a mistake.

## The evidence: what quantization costs and what it buys

Quantization stores a model’s weights in fewer bits than the 16 used at full precision. The format you will meet on Windows is **GGUF**, the file format of llama.cpp and of the tools built on that ecosystem. Three questions decide whether a quantized model is fit for production: how much smaller it gets, how much quality it loses, and how much faster it runs.

### Size: a 4-bit quant is under a third of full precision

llama.cpp’s quantize README publishes the effective bits per weight (bpw) of each type, measured on Llama-3.1-8B ([README](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md)). Effective bpw is always a little above the nominal figure because each block of weights also stores scales.

### Size versus bits: the old rule, and why it broke

For years the community rule of thumb was: at a fixed memory budget, take the bigger model at fewer bits. The original k-quants pull request, which introduced the Q2_K–Q6_K family in June 2023, contains the data behind that rule ([PR #1684](https://github.com/ggml-org/llama.cpp/pull/1684)). On LLaMA-1, every 13B quant — even Q2_K at 5.13 GB — had lower perplexity than the 7B model at full precision (13.0 GB).

That rule does not transfer cleanly to modern models. Compare the perplexity penalties for the same quant types on LLaMA-1 7B (from PR #1684) and on Llama-3-8B (from `quantize.cpp`). Llama 3 pays roughly three to four times as much at every level, and at Q2_K the penalty jumps from 0.87 to 3.52. An academic study of Llama 3 quantization reached the same qualitative conclusion: “non-negligible degradation”, “particularly under ultra-low bit widths” ([Huang et al.](https://arxiv.org/abs/2404.14047)). The usual explanation — which I offer as a hypothesis, not a finding — is that models trained on far more tokens pack more information into each weight, leaving less redundancy for quantization to discard.

The practical consequence is a revised rule: **the largest model that fits at 4–5 bits, never below about 3.5 bits without measuring on your own task.** “Bigger at 2 bits” was good advice for 2023 models; for 2025–2026 models it is a gamble.

### Speed: smaller weights, faster tokens

Generating each token requires reading essentially every weight from memory once, so on consumer hardware generation speed is largely limited by memory bandwidth. Fewer bytes per weight means more tokens per second. In llama.cpp’s current README, Llama-3.1-8B generated 71.9 tokens per second at Q4_K_M against 29.2 at F16 — about 2.5 times faster — on hardware the README does not specify. The k-quants PR gives a hardware breakdown for the 7B model (Exhibit 7).

Speed is a quality attribute in production. A model that streams at 60 tokens per second feels instant; one at 5 tokens per second makes a 300-token answer take a minute, and users abandon it. That is why the CPU rows matter: a 7B model at Q4_K_M on a desktop CPU is usable for a single user, while the same model at F16 is not.

## A framework: fit first, then choose

Most local-LLM projects I see start with “which model is best?” and end with a model that does not fit, spills into system RAM and crawls. I reverse the order. The decision stack below starts from the workload and the memory budget, and only then picks a model.

## Deep dive 1: how quantization actually works

It helps to know what the letters mean, because they predict behaviour.

**Block-wise quantization.** GGUF quant types do not use a single scale for a whole tensor. They split weights into small blocks and store a scale per block, so an outlier in one block does not ruin precision everywhere else. The simplest types are “type-0”, where a weight is reconstructed as w = d × q (a block scale times a small integer), and “type-1”, which adds a block minimum: w = d × q + m. Q4_0 and Q8_0 are the classic plain types.

**K-quants.** The k-quants introduced in PR #1684 add a second level. Weights are grouped into super-blocks of 256, split into sub-blocks of 16 or 32; the sub-block scales (and minimums) are themselves quantized to 4–8 bits, with one higher-precision scale per super-block ([PR #1684](https://github.com/ggml-org/llama.cpp/pull/1684)). That is why Q4_K is about 4.5 bpw and Q6_K about 6.56. The suffixes _S, _M and _L are **mixes**: the same base type for most tensors, but higher precision for the ones that hurt most when compressed. In the PR’s definition, Q4_K_M uses Q6_K for half of the attention.wv and feed_forward.w2 tensors and Q4_K elsewhere; Q3_K_M promotes attention.wv, attention.wo and feed_forward.w2 to Q4_K. This is the mechanism behind Exhibit 4’s gap between Q3_K_S and Q3_K_M: spending a few extra bits in the right tensors buys a large share of the quality back.

**I-quants.** The IQ types, introduced in early 2024, use a different trick at very low bit rates. IQ2_XXS, for example, quantizes weights in groups of eight and encodes their magnitudes as an index into a 256-entry codebook drawn from the E8 lattice, with signs stored using a parity trick — ideas the author credits partly to the QuIP# research ([PR #4773](https://github.com/ggml-org/llama.cpp/pull/4773)). The effect is better quality per bit at 2–4 bpw, at the cost of slower decoding on some hardware. IQ4_XS (4.46 bpw) is a useful alternative to Q4_K_M when a model is just slightly too big.

**Importance matrices.** Not all weights matter equally. llama.cpp’s `imatrix` tool runs calibration text through the model and records, for each weight column, the average squared activation; the quantizer then minimises error weighted by that importance rather than treating every weight alike ([PR #4861](https://github.com/ggml-org/llama.cpp/pull/4861); [imatrix README](https://github.com/ggml-org/llama.cpp/blob/master/tools/imatrix/README.md)). Importance matrices matter most at low bit rates. The practical upshot: when downloading 3-bit or IQ quants, prefer publishers who state they used an imatrix, and if you quantize yourself, calibrate on text that resembles your workload.

```powershell
# Build an importance matrix from calibration text, then quantize with it
llama-imatrix -m model-f16.gguf -f calibration-data.txt -ngl 99
llama-quantize --imatrix imatrix.gguf model-f16.gguf model-IQ4_XS.gguf IQ4_XS
```

**Quantization-aware training.** QAT, as in Google’s Gemma 3 release, goes further: the model is trained while simulating low-precision arithmetic, so it learns weights that survive quantization. Google reports that QAT reduced the perplexity drop at Q4_0 by 54% ([Google](https://developers.googleblog.com/en/gemma-3-quantized-aware-trained-state-of-the-art-ai-to-consumer-gpus/)). When a vendor ships an official QAT checkpoint, it is usually the best 4-bit option available.

**Failure mode and how to measure.** The characteristic failure of over-quantization is not gibberish; it is subtle drift — slightly worse instruction following, more formatting mistakes, weaker recall of rare facts. You will not see it in a demo. Measure it with a fixed evaluation set run against two or three quants of the same model, and compare against a hosted baseline.

## Deep dive 2: the memory arithmetic

A model needs memory for three things: its weights, its key-value (KV) cache, and working buffers.

**Weights** are approximately parameters × bits per weight ÷ 8. For Llama 3.1 8B at Q4_K_M: about 8 billion × 4.89 ÷ 8 ≈ 4.9 GB, matching the 4.92 GB file on Hugging Face ([bartowski](https://huggingface.co/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF)). For Llama 3.3 70B at Q4_K_M the file is 42.52 GB; at IQ2_XS it is 21.14 GB; at F16 it is 141.12 GB ([bartowski](https://huggingface.co/bartowski/Llama-3.3-70B-Instruct-GGUF)).

**KV cache** is the part people forget. For each token of context, the model stores a key and a value vector in every layer:

```text
KV bytes per token = 2 (K and V) × layers × KV heads × head dimension × bytes per element
```

The model configs give the inputs. Llama 3.1 8B has 32 layers, 8 KV heads and a head dimension of 128; Llama 3.3 70B has 80 layers, 8 KV heads and a head dimension of 128 ([8B config](https://huggingface.co/unsloth/Meta-Llama-3.1-8B-Instruct/blob/main/config.json); [70B config](https://huggingface.co/unsloth/Llama-3.3-70B-Instruct/blob/main/config.json)). At FP16 (2 bytes), that is 2 × 32 × 8 × 128 × 2 = 131,072 bytes, or 128 KiB per token, for the 8B model, and 2 × 80 × 8 × 128 × 2 = 327,680 bytes, or 320 KiB per token, for the 70B model. Multiply by context length.

## Deep dive 3: hardware tiers on Windows

The runtime documentation sets the floor. Ollama requires Windows 10 22H2 or newer ([Ollama, Windows](https://docs.ollama.com/windows)). For NVIDIA, it supports compute capability 5.0 and above with driver 550 or newer; cards of compute capability 5.0–6.2 need driver 570 or newer ([Ollama, GPU](https://docs.ollama.com/gpu)) — the Windows page itself lists 551.61 as the minimum, so simply install a current driver. For AMD on Windows, ROCm acceleration needs a ROCm v7 / HIP7-capable driver and a supported card — RX 7900 XTX, 7900 XT, 7900 GRE, 7800 XT, 7700 XT, 7600 XT, 7600 or the Radeon PRO W7000 series. Everything else can use **Vulkan**, which Ollama enables by default when the backend is installed (set `OLLAMA_VULKAN=0` to disable it). llama.cpp itself supports CUDA, HIP, Vulkan and SYCL (for Intel GPUs), among other backends ([llama.cpp](https://github.com/ggml-org/llama.cpp)). LM Studio requires AVX2 on x64 CPUs, runs on Snapdragon X Elite machines, and recommends 16 GB of RAM and 4 GB of dedicated VRAM ([LM Studio](https://lmstudio.ai/docs/app/system-requirements)).

**Step 1 — install and run a first model (Ollama).** Ollama installs into your user account without administrator rights and serves an API on `http://localhost:11434` ([Ollama, Windows](https://docs.ollama.com/windows)). You can pull a specific GGUF quant straight from Hugging Face:

```powershell
winget install Ollama.Ollama
# or: irm https://ollama.com/install.ps1 | iex

ollama run hf.co/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M
ollama ps   # check the model is 100% on GPU
```

**Step 2 — set context and memory deliberately.** Ollama’s documented default context window is 4,096 tokens, overridable with `OLLAMA_CONTEXT_LENGTH` or per request with `num_ctx` ([Ollama FAQ](https://docs.ollama.com/faq)). The KV cache can be quantized with `OLLAMA_KV_CACHE_TYPE` when Flash Attention is on: q8_0 uses about half the memory of f16 “with a very small loss in precision”; q4_0 about a quarter, with a loss that “may be more noticeable at higher context sizes”. Models live in `C:\Users\%USERNAME%\.ollama\models` unless you set `OLLAMA_MODELS`. On Windows, set these as user environment variables, then quit Ollama from the system tray and restart it:

```powershell
setx OLLAMA_CONTEXT_LENGTH 16384
setx OLLAMA_FLASH_ATTENTION 1
setx OLLAMA_KV_CACHE_TYPE q8_0
setx OLLAMA_NUM_PARALLEL 2
setx OLLAMA_MODELS "D:\models\ollama"
```

**Step 3 — or use LM Studio to compare quants.** LM Studio is the fastest way to try three quants of the same model side by side with a GUI. Since July 2025 it has been free for use at work as well as at home ([LM Studio](https://lmstudio.ai/blog/free-for-work)).

```powershell
winget install ElementLabs.LMStudio
```

**Step 4 — or llama.cpp for full control.** llama.cpp’s README now documents a unified `llama` command, plus a PowerShell installer (`irm https://llama.app/install.ps1 | iex`); older releases name the binaries `llama-cli` and `llama-server`. The server supports an API key, a context size, parallel slots and KV-cache types (`-c`, `-np`, `--api-key`, `-ctk`/`-ctv`), and binds to 127.0.0.1 by default ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

```powershell
winget install llama.cpp
llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF      # quick interactive test
llama serve -hf ggml-org/Qwen3.5-0.8B-GGUF    # OpenAI-compatible server
```

**Step 5 — serve it to applications.** All three expose OpenAI-compatible endpoints, which means existing client code needs only a base URL change. With Ollama the API key is required by the client library but ignored by the server ([Ollama](https://docs.ollama.com/api/openai-compatibility)):

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")
reply = client.chat.completions.create(
    model="hf.co/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M",
    messages=[{"role": "user", "content": "Summarise this clause in one sentence: ..."}],
)
print(reply.choices[0].message.content)
```

That portability is strategically important. If your application talks to an OpenAI-compatible interface, you can move a workload between local and hosted models by configuration — and you should design for exactly that, because the right answer for a workload changes as models and prices move.

### Production concerns

**Concurrency.** Ollama processes one request per model at a time by default and queues up to 512 more; raising `OLLAMA_NUM_PARALLEL` increases the context memory proportionally ([Ollama FAQ](https://docs.ollama.com/faq)). A single consumer GPU is a service for a team, not for a company. Load-test with realistic prompt lengths before you promise anyone a response time.

**Context length.** Set it explicitly and test at the limit. A silently truncated prompt is one of the most common causes of “the local model is worse” complaints in retrieval systems: the retrieved passages never reached the model.

**Network exposure.** Ollama binds to 127.0.0.1 by default and has no built-in authentication. Changing `OLLAMA_HOST` to expose it on a network without putting authentication in front is how incidents happen. In September 2025, Cisco researchers used Shodan to find 1,139 exposed Ollama servers, 214 of them actively hosting models ([Cisco](https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama)). Put a reverse proxy with authentication, or llama.cpp’s `--api-key`, in front of anything reachable from another machine, and restrict it to trusted networks.

**Model-file security.** A GGUF file is data, but the parser that reads it is code. In February 2024, Cisco Talos disclosed heap-overflow vulnerabilities in llama.cpp’s GGUF parsing, including CVE-2024-23605 (CVSS 8.8), where “a specially crafted .gguf file can lead to code execution” ([Talos](https://www.talosintelligence.com/vulnerability_reports/TALOS-2024-1916)). Treat model files like executables: download from known publishers, record a hash (`Get-FileHash model.gguf -Algorithm SHA256`), store approved files in a controlled location and keep runtimes updated.

**Licences.** “Open weights” is not one licence. Gemma 4, Qwen3.8, Mistral Small 4 and gpt-oss are Apache-2.0; DeepSeek V4.1-Flash is MIT; Llama models use Meta’s own licences. The Llama 3.1 Community License, for example, requires a separate licence if your products exceeded 700 million monthly active users, asks you to “prominently display ‘Built with Llama’” and binds you to an acceptable use policy ([Meta](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/LICENSE)). Read the model card before production, and record the licence alongside the hash.

**Updates.** Pin versions. A new runtime release can change defaults (context length, KV handling, GPU selection); a re-uploaded GGUF can change behaviour. Upgrade on a schedule, re-run your evaluation set, then promote.

## Case examples

**Google’s Gemma 3 QAT release (April 2025).** Google trained 4-bit-aware versions of Gemma 3 and published them for consumer GPUs, cutting the 27B model’s weights from 54 GB to 14.1 GB and reducing the Q4_0 perplexity drop by 54% compared with naive quantization ([Google](https://developers.googleblog.com/en/gemma-3-quantized-aware-trained-state-of-the-art-ai-to-consumer-gpus/)). *Lesson:* when a vendor ships a QAT checkpoint, it moves the quality-size frontier; start there.

**OpenAI’s gpt-oss (August 2025).** OpenAI post-trained its open-weight models with MXFP4 quantization of the mixture-of-experts weights and evaluated them in that form; the 20B model runs within 16 GB of memory under Apache-2.0 ([model card](https://huggingface.co/openai/gpt-oss-20b)). *Lesson:* quantization is no longer something the community does to a model after release — it is part of how frontier labs design open models for local hardware.

**Exposed Ollama servers (September 2025).** Cisco’s scan found over a thousand Ollama instances on the public internet without authentication ([Cisco](https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama)). *Lesson:* the easiest local runtime is also easy to misconfigure. The model was never the risk; the endpoint was.

**Field notes: an offline RAG system.** The privacy-first RAG system I mentioned at the start runs entirely on local hardware: Ollama serves Gemma 2 (2B or 9B) for generation and nomic-embed-text for embeddings, ChromaDB stores vectors on local disk, a FastAPI backend handles ingestion and queries, DVC versions each ingestion run, MLflow tracks retrieval experiments and Evidently monitors embedding and query drift. It uses CUDA where there is an NVIDIA GPU and Metal on a Mac, and it makes no outbound calls. Because the retrieval interface is identical to the cloud version, the only thing that changes between local and hosted is a model name.

<Note kind="insight">
In a retrieval-augmented system, retrieval quality usually moves answer quality more than model size does. A small model quantized to around 4 bits, answering from the right three passages, will beat a larger model answering from the wrong ten. Before you buy a bigger GPU, measure retrieval on your own evaluation set.
</Note>

## Counterpoints

<Note kind="counter" label="Objection 1">
Cloud APIs are cheaper and better. A small hosted model costs fractions of a cent per query, needs no hardware, and the frontier models are far more capable than anything that runs on a gaming card.
</Note>

<Note kind="response">
Mostly right on price, and Exhibit 2 says so: against Haiku-class pricing, a GPU takes close to a million queries to pay back. It is also right on peak capability. But the objection assumes the hosted option is available. For residency-bound data, offline sites and air-gapped networks it is not, and the relevant comparison is a local model versus no model. Where both are allowed, I default to hosted and move workloads local only when volume, latency or control justify it — which an OpenAI-compatible interface makes cheap to revisit.
</Note>

<Note kind="counter" label="Objection 2">
Small local models hallucinate more. An 8B model simply knows less than a frontier model, and quantization makes it worse.
</Note>

<Note kind="response">
True for open-domain questions: a smaller model has less parametric knowledge, and you should not ask it to recall facts. That is why local models belong in grounded patterns — retrieval-augmented answering, extraction, classification, summarisation of supplied text — with instructions to refuse when the context lacks the answer, and an evaluation set that checks for it. The quantization part of the objection is true below about 3.5 bits on modern models and largely false at 5–8 bits.
</Note>

<Note kind="counter" label="Objection 3">
Quantization ruins reasoning. Perplexity barely moves, but multi-step reasoning collapses.
</Note>

<Note kind="response">
Partly right, and it is why I do not treat perplexity as the decision metric. A 2025 study of quantized reasoning models found that W8A8 or W4A16 (4-bit weights, 16-bit activations — the regime GGUF 4-bit quants occupy) can be close to lossless, while “lower bit-widths introduce significant accuracy risks”, with model size and task difficulty as key determinants ([Liu et al.](https://arxiv.org/abs/2504.04823)). That supports a 4-bit floor, not a blanket rejection — and it argues for testing reasoning-heavy tasks specifically.
</Note>

## Implications by stakeholder

**Executives and risk owners.** Local inference converts a data-protection question into an infrastructure question. That is a good trade for regulated data, and a poor one for everything else. Ask for the eligibility case (step one of Exhibit 8) in writing, and expect to fund evaluation and security work, not just hardware.

**Engineering leads.** Design every LLM call behind an OpenAI-compatible interface with the model name in configuration, so workloads can move between local and hosted without code changes. Own the operational basics: authenticated endpoints, pinned model hashes, scheduled upgrades with regression runs, and monitoring of GPU residency and latency.

**Practitioners.** Learn the memory arithmetic and the quant ladder well enough to size a deployment on a napkin. Build a small, honest evaluation set early; it is the only thing that will settle arguments about which quant or model to use.

**Security and compliance teams.** Treat GGUF files and runtimes as software supply chain: approved sources, hashes, version control and patching. Treat a local LLM endpoint as an unauthenticated API until proven otherwise.

## What to do next: a 90-day plan

**Days 1–30: decide and size.**
1. List candidate workloads and mark which have a residency, offline, control or volume reason. Drop the rest.
2. For each survivor, record the real context length and concurrency. Run the Exhibit 10 arithmetic.
3. Build an evaluation set of 50–100 real inputs with expected answers or rubrics, and score the hosted baseline.
4. On existing hardware, test two or three quants (Q4_K_M, Q5_K_M, Q6_K) of one or two licence-compatible models in LM Studio or Ollama.

**Days 31–60: pilot.**
5. Stand up Ollama or llama.cpp on one machine with explicit context, KV-cache type and parallelism settings.
6. Put authentication in front of it, restrict it to the internal network, and record model hashes and licences.
7. Run a pilot with real users; log latency, GPU residency and failure cases, and re-score the evaluation set.

**Days 61–90: harden or hand back.**
8. If the local model is within an acceptable margin of the baseline on your evaluation set, harden: monitoring, upgrade cadence, runbooks.
9. If not, try the next tier up (bigger model or higher quant) once. If it still fails, return the workload to a hosted model — and keep the interface, so you can try again when the next open-weight generation arrives.

## Limitations and methodology

The quality evidence is perplexity, measured mostly on two models: Llama-3-8B for the current deltas and LLaMA-1 7B/13B for the size comparison. Perplexity is a proxy; it does not measure instruction following, grounding or reasoning, and its values are not comparable across models with different tokenizers. The cross-generation comparison in Exhibit 6 mixes evaluation runs and llama.cpp versions and should be read as directional.

Speed figures are hardware-dependent. The README’s 2.5× speed-up does not state its hardware; the PR #1684 timings are from a 2023 build on a 2023 model. Absolute speeds on current builds will differ; ratios are more stable. The memory figures are calculations from published configs and file sizes plus my own rule of thumb for buffers; your runtime will report slightly different numbers. The break-even estimate uses list prices on 14 October 2026, one GPU’s launch price, and an assumed token mix; it ignores electricity, the rest of the machine and the capability gap. I have not presented benchmarks of my own here, and the field note above is flagged for confirmation.

## Closing

The question “can I run a real model on a Windows PC?” has been answered: yes, and with the right quant it is fast enough to use. The more useful question is whether you should, and if so, how to fit it. For workloads where data cannot leave, networks cannot be relied on, or volume is high and steady, a well-quantized open-weight model is a credible production choice. Make the decision in the right order — eligibility, memory budget, quant floor, then the largest model that fits — secure the endpoint like any other service, and let your own evaluation set, not a leaderboard, have the final word.
