<p class="lede">A web app with a real database used to need a server, a bill and a weekend. In October 2026 it needs about an hour and no card: a static front end on Vercel's Hobby plan, a Postgres database on Supabase's Free plan, and a GitHub repository joining the two. The catch is that the cheapest part of this stack, a database key you deliberately ship to every visitor's browser, is also the part that has leaked data from real apps.</p>

This is a step-by-step tutorial. We will deploy **Budget Board**, a deliberately small public message board: anyone can read and post messages of up to 280 characters, and nobody can edit or delete them. It is about 200 lines of TypeScript and HTML with no framework, so every moving part is visible. By the end you will have a live URL, preview deployments on every pull request, an optional custom domain and spend guardrails, all on free tiers whose limits I checked against the vendors' own pricing and documentation pages on 14 October 2026.

My argument is this: **for a personal project or prototype, Vercel Hobby plus Supabase Free is the quickest credible $0 stack available today, but it is safe only when Row Level Security and explicit grants are treated as the real security boundary, and it is the wrong stack the moment the project earns money, needs an always-on server or cannot tolerate a paused database.** The tutorial is the heart of the piece. Around it sits the analysis that tells you whether to follow it at all: what the free tiers actually include, which limit bites first, what happens when you hit it, and which alternative to pick for which job.

## Context: why this matters now

Free tiers are a product decision, and vendors revise them. Three changes in the past two years alter how a budget deployment should be built in late 2026.

**The rules of the free tiers moved.** Fly.io no longer gives new organisations a free allowance; only accounts on plans discontinued in October 2024 keep theirs ([Fly.io](https://docs.fly.io/about/pricing)). Netlify's Free plan is now a pool of 300 credits a month with a hard limit, and production deploys, bandwidth and requests all draw from it ([Netlify](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/)). Vercel restructured Pro in September 2025 around a $20 monthly usage credit and switched spend management on by default ([Vercel](https://vercel.com/blog/new-pro-pricing-plan)).

**Supabase changed how tables reach the internet.** On 28 April 2026, Supabase announced that new tables in the `public` schema would no longer be exposed to its Data API automatically. That became the default for new projects from 30 May 2026 and applies to all existing projects from 30 October 2026 ([Supabase changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)). Supabase is also deprecating its legacy `anon` and `service_role` keys by the end of 2026 in favour of **publishable** (`sb_publishable_…`) and **secret** (`sb_secret_…`) keys ([Supabase](https://supabase.com/docs/guides/api/api-keys)). Most tutorials written before 2026 use the old key names and skip the grants, so they now fail in confusing ways.

**The cost of getting security wrong became concrete.** In March 2025, Matt Palmer found that sites built with the AI app builder Lovable were exposing Supabase tables to anyone holding the public key. His scan of 1,645 showcased projects found 303 vulnerable endpoints across 170 projects, about 10.3%, including user emails, phone numbers and payment details ([Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). It was published as CVE-2025-48757 with a CVSS 3.1 score of 9.3; Lovable disputes it on the grounds that each customer is responsible for protecting their own application's data ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-48757)). Whichever side you take on blame, the mechanism is the one this tutorial is built around.

## A framework: the three-gate test

Before you type a command, decide whether this stack fits the job. I use three gates, in order. A project that passes all three should use Vercel Hobby plus Supabase Free without guilt; a project that fails one should change one component, not abandon the approach.

**Gate 1, purpose,** is contractual, not technical. A portfolio, a hackathon demo, a learning project or a free community tool passes. A client site, a shop or a SaaS fails on Vercel Hobby, and GitHub Pages carries a similar restriction: it "is not intended for or allowed to be used as a free web-hosting service to run your online business, e-commerce site" or commercial SaaS ([GitHub](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).

**Gate 2, persistence,** separates static-plus-database apps from apps that need a server running. Budget Board has no server of its own: the browser talks straight to Supabase. If your app needs background jobs, WebSockets you host yourself or long-running processes, a container host is a better fit, and the free ones there sleep (Render) or are trials (Railway, Fly.io).

**Gate 3, permissions,** is the one that the Lovable incident failed. On this stack the database is reachable from the public internet by design. The only thing between a visitor and your tables is the combination of grants and Row Level Security you write. If you cannot state the rules in a sentence per table, you are not ready to deploy.

## How the stack works: two locks on one door

It helps to see the request path before building it. When a visitor opens Budget Board, Vercel's CDN serves three static files: HTML, CSS and a JavaScript bundle. That bundle contains the Supabase project URL and the publishable key, because Vite compiles every variable prefixed `VITE_` into client code. The browser then calls Supabase's Data API directly.

Supabase's documentation is blunt about what that key is. A publishable key is "safe to expose online", but "anyone can read it, so it only reaches what Row Level Security allows", and you should "enable it on every table before you deploy" ([Supabase](https://supabase.com/docs/guides/api/api-keys)). Secret keys, by contrast, bypass RLS and must never appear in "a browser, a shipped application, or source control".

Grants answer "may this role touch the table at all?"; policies answer "which rows?". Supabase's documentation describes the danger case precisely: "A table in an exposed schema without RLS is readable and writable by any role with a grant on it" ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)). The 2026 grants change helps here, because a table you forget about is no longer exposed by default, but it also means a correct schema must now state its grants explicitly. Our schema does both.

## The tutorial: deploy Budget Board in thirteen steps

You need Node.js 22.12 or newer (Vite 8 requires `^20.19.0 || >=22.12.0`), Git, and free accounts on GitHub, Supabase and Vercel. Sign in to Vercel with GitHub; it makes step 7 a two-click import. Total time is about an hour on a first run.

### Step 1: create the project

Scaffold a vanilla TypeScript project with Vite and add the Supabase client. The `--` before `--template` is required on npm 7 and later ([Vite](https://github.com/vitejs/vite/tree/main/packages/create-vite)).

```bash
npm create vite@latest budget-board -- --template vanilla-ts
cd budget-board
npm install @supabase/supabase-js
```

The finished app has six files that matter. I pinned exact versions as published on npm on 14 October 2026, so the build you run is the build I tested: `vite` 8.3.4, `typescript` 7.0.2 and `@supabase/supabase-js` 2.117.3.

```text
index.html            page shell: form, message list, "test the lock" button
src/main.ts           Supabase client, list, post, test the lock
src/style.css         small dark theme
src/vite-env.d.ts     types for import.meta.env
supabase/schema.sql   table, grants, RLS policies
.env.example          variable names, no real values
```

The core of `src/main.ts` is short. It reads two environment variables, refuses to start if either is missing or if someone has pasted a secret key, and renders untrusted message text with `textContent`, never `innerHTML`, so a posted `<script>` tag is displayed rather than executed.

```ts
import { createClient } from '@supabase/supabase-js';

const url = import.meta.env.VITE_SUPABASE_URL;
const key = import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY;

if (!url || !key) throw new Error('Set VITE_SUPABASE_URL and the publishable key');
if (key.startsWith('sb_secret_')) {
  throw new Error('Secret keys bypass RLS and must never ship to a browser');
}

const db = createClient(url, key);

// Read the 50 newest messages
const { data, error } = await db
  .from('messages')
  .select('id, created_at, body')
  .order('created_at', { ascending: false })
  .limit(50);

// Post a message (the database re-checks the length)
await db.from('messages').insert({ body: text.trim() });
```

The real file wraps those calls in small functions, a character counter and a "Test the lock" button that tries to delete the newest message with the public key and reports whether the database refused. That button is how you will verify the security model in step 10. In the demo build the whole bundle is 56.4 KB of JavaScript after gzip, most of it the Supabase client.

### Step 2: create the Supabase project

In the Supabase dashboard, create a new project. Give it a name, generate a strong database password and store it in a password manager (you will not need it for this tutorial, but you will for backups or direct connections), and pick the region closest to your users. If the creation form offers Data API options, leave the Data API enabled; our schema grants access explicitly, so it works whichever exposure default your project has.

The Free plan allows two active free projects across all organisations you own or administer; paused projects do not count ([Supabase](https://supabase.com/docs/guides/platform/billing-on-supabase)). Spend that second slot wisely: step 11 suggests using it as a staging database.

### Step 3: run the schema in the SQL Editor

Open **SQL Editor**, start a new query, paste the file below and click **Run**. It is safe to re-run.

```sql
-- 1. The table. The CHECK constraint enforces the 1-280 character rule
--    in the database itself, even for requests that skip the web page.
create table if not exists public.messages (
  id         bigint generated always as identity primary key,
  created_at timestamptz not null default now(),
  body       text not null check (char_length(body) between 1 and 280)
);

-- 2. Row Level Security ON. With RLS on and no matching policy,
--    the Data API returns nothing and changes nothing.
alter table public.messages enable row level security;

-- 3. Lock 1, grants: which roles may touch the table at all.
revoke all on table public.messages from anon, authenticated;
grant select, insert on table public.messages to anon, authenticated;

-- 4. Lock 2, policies: which rows those roles may read or write.
drop policy if exists "Anyone can read messages" on public.messages;
create policy "Anyone can read messages"
  on public.messages for select
  to anon, authenticated
  using (true);

drop policy if exists "Anyone can post a message" on public.messages;
create policy "Anyone can post a message"
  on public.messages for insert
  to anon, authenticated
  with check (char_length(body) between 1 and 280);

-- 5. Deliberately no UPDATE or DELETE policy and no grant for them.
```

Three design choices are worth explaining. The `revoke all` line matters for projects created before the grants change, where `anon` would otherwise have inherited update and delete privileges on new tables; revoking first makes the result identical on old and new projects. The policies name `anon, authenticated` explicitly rather than relying on defaults, which is the pattern Supabase's own examples use for public data, with the warning to use it "only for data that is meant to be public" ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)). And the length rule appears three times on purpose: in the browser for a friendly message, in the insert policy, and in the table's CHECK constraint, which no client can bypass.

To confirm, run `select policyname, cmd, roles from pg_policies where tablename = 'messages';`. You should see two rows, one for `SELECT` and one for `INSERT`.

### Step 4: copy the project URL and the publishable key

Open the project's **Connect** dialog, or **Settings > API Keys**, and copy two values: the project URL (`https://<project-ref>.supabase.co`) and the **publishable** key, which starts `sb_publishable_` ([Supabase](https://supabase.com/docs/guides/api/api-keys)).

<Note kind="warn" label="The one key that must never leave the server">
Do not copy a secret key (`sb_secret_…`) or the legacy `service_role` key into anything that starts with `VITE_`. Both bypass Row Level Security, and anything prefixed `VITE_` ends up in a JavaScript file every visitor downloads. If you ever paste one by mistake and push it, rotate it in Settings > API Keys immediately; deleting the commit is not enough.
</Note>

### Step 5: run it locally

Create `.env.local` from the example and fill in both values. The `.gitignore` excludes every `.env*` file except `.env.example`, so real values are never committed.

```bash
cp .env.example .env.local
# edit .env.local:
# VITE_SUPABASE_URL=https://<project-ref>.supabase.co
# VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...

npm run dev      # http://localhost:5173
npm run build    # type-check, then production build into dist/
```

Post a message. If the list shows "Could not load messages", the usual causes are a typo in the URL, a missing grant (re-run step 3) or a paused project.

### Step 6: push the repository to GitHub

Create an empty repository on GitHub, then push. With the GitHub CLI it is one command; otherwise add the remote by hand.

```bash
git init
git add .
git commit -m "Budget Board: Vite + Supabase"
git branch -M main

# Option A: GitHub CLI
gh repo create budget-board --public --source=. --push

# Option B: an empty repo you created on github.com
git remote add origin https://github.com/<you>/budget-board.git
git push -u origin main
```

Before pushing, run `git status` and check that `.env.local` is not listed. A public repository is fine here: nothing in it is secret. If you prefer private, note one Hobby restriction: for private repositories, Vercel deploys only commits authored by the Hobby team's owner, and the Hobby plan "does not support collaboration for private repositories" ([Vercel](https://vercel.com/docs/deployments/troubleshoot-project-collaboration)).

### Step 7: import the repository into Vercel

In Vercel, choose **Add New… > Project**, find `budget-board` in the list of GitHub repositories and click **Import**. Vercel detects Vite and fills in the build settings; leave them as they are.

Budget Board is a single page, so it needs no `vercel.json`. If you later build a single-page app with client-side routes, Vercel's Vite guide shows the rewrite to `/index.html` that makes deep links work ([Vercel](https://vercel.com/docs/frameworks/frontend/vite)).

### Step 8: set the environment variables

Still on the import screen, open **Environment Variables** and add the two values from step 4. If you have already deployed, use **Settings > Environment Variables** instead.

| Name | Value | Environments |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | `https://<project-ref>.supabase.co` | Production, Preview |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` | Production, Preview |

Two details trip people up. First, Vite reads these values at **build** time and bakes them into the bundle, and Vercel is explicit that "any change you make to environment variables are not applied to previous deployments, they only apply to new deployments" ([Vercel](https://vercel.com/docs/environment-variables)). After editing a variable, redeploy. Second, Vercel now asks whether each variable is a Config or a Secret value. The publishable key is public by design, so Config is honest; marking it Secret hides it in the dashboard but does not hide it from browsers.

### Step 9: deploy

Click **Deploy**. The build runs `tsc --noEmit && vite build`, which type-checks before bundling, so a type error fails the deployment instead of shipping. A successful build ends with a production URL on `vercel.app`.

### Step 10: test it, including the part that should fail

Open the production URL. Then test four things, in this order.

1. **Read.** The list loads, with the test message from step 5.
2. **Write.** Post a new message; it appears at the top.
3. **Reject.** Click **Test the lock**. The page should report "Blocked, as intended" with a permission error, because `anon` has no DELETE grant and there is no DELETE policy. If it ever reports rows deleted, stop and revisit step 3.
4. **Bypass the page.** The real attacker does not use your UI. Call the API directly with the same public key:

```bash
URL=https://<project-ref>.supabase.co
KEY=sb_publishable_...

# Read: returns a JSON array of messages
curl -s "$URL/rest/v1/messages?select=id,body&limit=3" -H "apikey: $KEY"

# Delete everything: must be refused
curl -s -X DELETE "$URL/rest/v1/messages?id=gt.0" -H "apikey: $KEY"

# Oversized insert: must be rejected by the policy or the CHECK constraint
curl -s -X POST "$URL/rest/v1/messages" -H "apikey: $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"body\": \"$(printf 'x%.0s' {1..300})\"}"
```

Supabase asks for publishable and secret keys on the `apikey` header, "not on `Authorization: Bearer`" ([Supabase](https://supabase.com/docs/guides/api/api-keys)). The delete should return a permission error; the 300-character insert should fail. Finally, open **Table Editor** in Supabase and confirm that your messages are there and nothing else is.

### Step 11: preview deployments on a pull request

This is the feature that makes Vercel worth choosing even at $0. Every push to a branch other than `main` gets its own preview URL, and pull requests get a comment linking to it.

```bash
git checkout -b tweak-tagline
# edit the tagline in index.html
git commit -am "Friendlier tagline"
git push -u origin tweak-tagline
gh pr create --fill
```

Once the preview build finishes, the Vercel bot comments on the pull request with a preview link. Review the change there, merge, and Vercel deploys `main` to production.

Two settings decide how useful previews are. **Who can see them:** Deployment Protection's Standard Protection, available on all plans, protects every deployment except production domains, and with Vercel Authentication only signed-in members of your Vercel team get through ([Vercel](https://vercel.com/docs/deployment-protection)); check **Settings > Deployment Protection** before sharing a preview link with someone outside the team. **Which database they use:** with the variables from step 8, previews write to your production database. For a toy that is fine. For anything with real users, create your second free Supabase project as staging, run the same `schema.sql` there, and set its URL and key as **Preview**-only variables. Vercel applies preview variables to every non-production branch, and branch-specific values override them ([Vercel](https://vercel.com/docs/environment-variables)).

### Step 12: add a custom domain (optional)

In the project, open **Settings > Domains** and add your domain. Vercel shows the exact DNS records to create at your registrar: an **A** record for an apex domain such as `example.com`, or a **CNAME** for a subdomain such as `board.example.com`, where each project has its own unique CNAME target ([Vercel](https://vercel.com/docs/domains/working-with-domains/add-a-domain)). Copy the values from your dashboard rather than from a blog post, including this one. If you add an apex domain, Vercel prompts you to add `www` as well and redirect one to the other. Hobby allows up to 50 domains per project.

The domain is the only line in this tutorial that costs money, and it is a registrar fee, not a hosting fee.

### Step 13: put guardrails on cost and know your upgrade trigger

On the free tiers there is no bill to run up: Vercel Hobby accounts "cannot purchase additional usage" ([Vercel](https://vercel.com/pricing)), and Supabase Free usage is not charged. The risk is not money but downtime. So the guardrails on free are about noticing, and the guardrails on paid are about capping. Write both down now; the next section explains the numbers.

- **Watch usage monthly.** Vercel's **Usage** tab shows transfer, CDN requests and function usage against the Hobby limits; Supabase's **Usage** page shows database size, egress and MAU.
- **Decide what happens when Supabase pauses.** If a week without traffic is plausible, either accept a manual restore or plan to move to Pro. Do not run a scheduled job just to defeat the pause; it works against the spirit of a free tier you depend on.
- **Before upgrading, configure the caps.** On Vercel Pro, set an on-demand budget and turn on **Pause Production Deployments**. On Supabase Pro, leave the Spend Cap on until you have a reason to turn it off.

## Deep dive 2: the security model, and how the Lovable apps failed

The Lovable exposure is the clearest public case of what goes wrong on this exact architecture, and the numbers are worth holding in your head.

Palmer's write-up lists what was reachable: user tables with emails, names and phone numbers, transactions and payment details, and third-party API keys stored in the database ([Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). Nothing about the hosting or the key was unusual. The publishable key (then the `anon` key) was in the bundle exactly as Supabase intends. The failure was that the tables behind it either had RLS off or had policies that did not express the intended rules.

Three practices close that gap, and Budget Board uses all of them.

- **Default deny, then allow narrowly.** Turn RLS on in the same script that creates the table, so there is never a moment when the table is exposed without it. With RLS on and no policy, Supabase returns nothing through the publishable key ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)).
- **Grant only the verbs you mean.** Budget Board grants `select` and `insert`, not `all`. Since the 2026 change, explicit grants are required anyway; use the requirement to be precise rather than copying the broad `select, insert, update, delete` example meant for authenticated users ([Supabase changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)).
- **Test as the attacker.** Step 10's `curl` calls use only what any visitor has: the URL and the publishable key. If those calls can read or change something they should not, so can anyone.

Never store third-party API keys in a table the browser can read. If the app needs to call a paid API, that call belongs in a server-side function holding a secret, which is the point at which Budget Board's "no server" design stops being enough.

## Case examples

**The Lovable exposure (2025).** Covered above, and worth restating as a lesson for anyone using an AI app builder: the generated code put the public key in the browser exactly as intended, and about one in ten scanned projects had not expressed their access rules in the database ([Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). *Lesson:* when a tool writes your schema, read the grants and policies yourself, then run the step 10 tests.

**Supabase's grants change (2026).** A platform default changed underneath existing tutorials. A table created by raw SQL in a project on the new default is invisible to the Data API until granted, which shows up as empty results or "not found" errors rather than an obvious permission failure ([Supabase changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)). *Lesson:* keep schema, grants and policies together in one versioned SQL file, so the security model is code you can review, not dashboard clicks you have to remember.

**Render's free web services.** A free web service on Render spins down after 15 minutes without inbound traffic and takes about a minute to spin back up; a free Postgres database expires 30 days after creation ([Render](https://render.com/docs/free)). *Lesson:* "free" can mean free and slow to wake. That is fine for a demo you open before a meeting, and wrong for anything a stranger will try once and abandon.

This portfolio is the static end of the same spectrum. It is an Astro site hosted free on GitHub Pages and deployed by a GitHub Actions workflow, with a daily scheduled rebuild that publishes future-dated posts. The third-party deploy action is pinned to a commit SHA, and job permissions are scoped: the build job can only read the repository, and only the deploy job can write to Pages. It has no database, so it never needed the second half of this tutorial, and it is a portfolio rather than a business, which keeps it inside GitHub Pages' usage rules.

## Counterpoints

<Note kind="counter" label="Objection 1">
Putting a database key in the browser is insecure, full stop. A real app should have a backend in front of the database.
</Note>

<Note kind="response">
The objection mistakes the key for the boundary. A publishable key identifies the project, the way a hostname does; Supabase says so plainly and tells you to rely on RLS ([Supabase](https://supabase.com/docs/guides/api/api-keys)). A backend that holds a secret key and forwards requests moves the same authorisation rules from SQL policies into application code, where they are no easier to get right. The architecture is sound when the rules are explicit and tested, which is why step 3 and step 10 exist. The objection is right in one case: anything requiring a secret, such as calling a paid third-party API, needs server-side code.
</Note>

<Note kind="counter" label="Objection 2">
Free tiers are a trap. You build on them, the terms change, and you are locked in.
</Note>

<Note kind="response">
Exhibit 1 shows terms do change, so the risk is real. But lock-in on this stack is low by construction: the front end is a `dist/` folder any static host can serve, and the database is standard Postgres you can export with `pg_dump` using the password from step 2. The mitigation is to stay portable on purpose: keep schema and policies in a versioned SQL file, avoid platform-specific features until you need them, and re-check the pricing pages before each launch.
</Note>

<Note kind="counter" label="Objection 3">
Nobody enforces the non-commercial rule. Freelancers ship client sites on Hobby all the time.
</Note>

<Note kind="response">
Whether it is enforced is not the question; whether you can defend it to a client is. Vercel's definition explicitly covers "a paid employee or consultant writing the code" ([Vercel](https://vercel.com/docs/limits/fair-use-guidelines)), and Hobby accounts cannot buy more usage when a launch goes well. $20 a month is a small line in any paid engagement. Build on Hobby, and move the project to a Pro team before the client's first real user arrives.
</Note>

<Note kind="counter" label="Objection 4">
A $5 VPS gives you a real server, a real database and no limits for less than either Pro plan.
</Note>

<Note kind="response">
For an engineer who wants to run servers, yes, and Exhibit 8 shows cheaper single-purpose steps exist. But the VPS price excludes the work: patching, TLS, backups, monitoring and recovery. The managed stack's value is preview deployments, HTTPS, a global CDN and a database dashboard with no operations time, which matters most at exactly the stage when a project is free. Choose the VPS when you want to learn operations or need always-on processes; choose the managed stack when your scarce resource is time.
</Note>

## Implications by stakeholder

**Students and job-seekers.** This stack turns a portfolio project from screenshots into a live URL a recruiter can click, at $0. The security steps are the differentiator: a short README section showing the grants, the policies and the `curl` tests that prove them says more about your judgement than another feature does.

**Freelancers and consultants.** Prototype on free tiers, but price Vercel Pro (and Supabase Pro if the client cannot tolerate pausing) into every paid engagement, and create the projects in an account or team the client will own. Hand over the SQL file along with the code.

**Founders.** The free stack is a good place to find out whether anyone wants the product. Write your upgrade trigger before launch, for example "first paying customer or 50% of any free limit", and configure the spend controls at the same time. About $45 a month is a small price for not discovering a paused database during a demo.

**Engineering and security leads.** If your organisation uses AI app builders or lets teams spin up Supabase projects, require the same review you would for any public API: RLS on every exposed table, explicit grants, no secret keys in client code, and an automated test that runs the step 10 calls against preview deployments.

## What to do next: a pre-launch checklist

Run this list before you share the URL with anyone you do not know.

1. **Gate 1 passed in writing.** No one is paid to build it and it sells nothing; otherwise you are on Vercel Pro.
2. **Schema in version control.** One SQL file creates the table, enables RLS, grants specific verbs and defines every policy.
3. **RLS on every exposed table.** Check **Table Editor** for the RLS badge, or query `pg_tables` where `rowsecurity` is false in the `public` schema.
4. **Only the publishable key in client code.** Search the built `dist/` folder for the first ten or so characters of your real secret key; there should be no match. Do not search for the bare prefix `sb_secret_`: the Supabase client library contains that string itself, so the demo's bundle matches it with no secret present.
5. **Attacker tests pass.** The step 10 `curl` calls refuse deletes and oversized inserts.
6. **Untrusted text rendered safely.** `textContent`, not `innerHTML`, for anything users write.
7. **Previews isolated.** Preview variables point at a staging project if real users write data.
8. **Pausing decided.** Either accept manual restores or schedule the move to Supabase Pro.
9. **Usage reviewed monthly.** Note the two numbers from Exhibit 5 that bind first: CDN requests and database egress.
10. **Caps configured before upgrading.** Vercel on-demand budget with Pause Production Deployments; Supabase Spend Cap left on.

## Closing

The budget stack is no longer a compromise. For the price of nothing, a small app gets a global CDN, preview deployments, a managed Postgres database and automatic certificates, in an hour. What it does not get is a server-side safety net: the database is on the public internet, the key is in every browser, and the only things standing between a visitor and your data are a dozen lines of SQL you either wrote deliberately or did not write at all. Write them first, test them like an attacker, and the free tier will carry you further than you expect. The key was never the secret. The policy is.
